Abstract

We built an integrated, educational financial-analysis system for 30 BIST 100 stocks in which the language model interprets and explains, deterministic Python tools compute, a stateful harness controls, and a backtest verifies. The model runs entirely locally (Ollama, Q4_K_M GGUF); no cloud AI API is used. We fine-tuned Gemma 3 4B with QLoRA on 600 tool-using sessions generated from real tool outputs, with action labels derived by a deterministic policy and explanations assembled from locked evidence.

On a 40-question held-out test (11 question types) run under five harness profiles (A: raw LLM ... E: memory and human review) for both the base and the fine-tuned model (400 sessions on a Kaggle T4), fine-tuning raised the number of delivered answers in the full harness (profile D) from 1/40 to 30/40 and cut numerical hallucination in the tools-only profile from 83.3% to 0.0%. In the full harness, the delivered answers contained 0% numerical hallucination, 0% rule violations and 100% agreement with the policy label; this guarantee comes from the harness (number verifier, action guard, locked evidence), not from the model alone. We also report weaknesses openly: about 25% of full-harness sessions are safely cut off at the 40-turn limit, live reproducibility is only 47%, and without the harness the fine-tuned model is not reliable by itself.

1. Problem and objective

Problem. A small local language model answering financial questions can invent numbers, call the wrong tool or use wrong parameters, state conclusions without evidence, give investment advice, or use information from after the analysis date (look-ahead bias). The course project measures exactly these failures: numerical hallucination rate, invalid tool-call rate, unsupported-conclusion rate, evidence integrity and reproducibility, and rule violations.

Objective. Answer the four mandatory scenarios (sector laggard/catch-up, weekday and multi-day patterns, technical reversals, quarterly fundamentals and post-disclosure price reaction) plus a macro-context scenario in a reliable and auditable way, using a fine-tuned local LLM inside a stateful harness. The evaluation question is not “which LLM is best” but how much more reliable and reproducible the system becomes as tools, states, evidence/quality gates, verification and human review are added.

Scope decisions. News and speech tools (get_news_events, get_speech_features) were not implemented. The macro tool is real (USDTRY, EURTRY, CPI, and the CBRT funding cost; the policy rate series is not used). All limitations are listed in Section 9.

Key design decisions

  • Common tool envelope. All tools return the same envelope (tool, params, as_of, data_version, input_hash, results, n_events, n_excluded_incomplete_horizon, warnings, status); the schema is versioned (current 1.5.0) and changes only by explicit agreement.
  • Zero look-ahead. as_of is mandatory for every tool; events whose forward horizon (1/3/5/10/20 days) extends past as_of are excluded from statistics and reported as n_excluded_incomplete_horizon; fundamentals are aligned by KAP disclosure date and macro data by publication date.
  • Mandatory steps derived from the tools the model calls (not from question classification): quality gate, evidence bundle and risk gate always; calling rank_sector_relative_strength additionally requires run_backtest. Skipping a mandatory step, a bad as_of or a schema error is always a hard failure.
  • Two-stage locked evidence bundle. Stage 1: observational analyses; stage 2: backtest evidence and final gate; then the bundle is locked (lock_hash). Every number in an evidence sentence is copied verbatim from a source envelope; the harness never derives new numbers.
  • Quality gate outputs PASS, PASS_WITH_WARNINGS, INVESTIGATE, ANALYSIS_UNSAFE, HARD_BLOCK; on HARD_BLOCK/ANALYSIS_UNSAFE the model's tool is not run and a safe failure path is taken.
  • Number verifier and action guard. Every number in the final text is classified (ALLOWLISTED, SUPPORTED, UNEVIDENCED, HALLUCINATION); the final line must be EYLEM: <LABEL> (the action line), the label must be in the allowed set and equal to the policy label, and advice language (BUY/SELL, price targets, certainty claims) is forbidden. A quoted refutation (“the claim that it will certainly rise is unverified”) is exempt.
  • Label policy in code. The label is computed deterministically by label_policy.decide_label and is identical in training, evaluation and the live test; the model explains it. This is why action agreement in profiles D/E is 100%.
  • Model view. The envelope shown to the model contains only the fields evidence can quote (context budget 8192 tokens); the full envelope stays with policy and verifier.
  • Local model, no cloud. The Ollama client accepts only loopback addresses. Tool calls for Gemma 3 use a text protocol (<tool_call>/<tool_response>); the prompt is rendered byte-for-byte like the training text and sent through the raw generate endpoint.
  • Parameter fixer and scope guard (added after evaluation): see Section 6.4.

5. Fine-tuning

5.1 Base model

Gemma 3 4B (unsloth/gemma-3-4b-it), 4-bit QLoRA. The instructor recommended open models of 1–8B parameters trained with LoRA/QLoRA; the model fits one 16 GB T4 for training and runs locally as a 2.5 GB Q4_K_M GGUF under Ollama. We did not compare other base models (Section 9). Context length is 8192 tokens.

5.2 Training data (generator version 2.3, seed 42)

Each record is: question, tool calls, tool outputs, evidence-grounded explanation plus the action line. The training text is identical to the text the model sees at inference; loss is computed only on assistant turns (tool calls and final text). The label comes from the policy; the explanation is assembled by rule from locked evidence sentences (no LLM is used to write training data). Only real v2 tool outputs are used.

5.4 Running locally

ollama create gemma3-bist-v23 -f training/ollama/Modelfile.v23 registers the GGUF with our chat template (no <bos> in the template). A template check (python -m experiments.check_template) confirms the prompt is token-for-token identical to the training text. Engineering finding: Ollama's chat endpoint produced 3 extra tokens for the first message and 4 more per assistant turn compared with the training text, independent of the template; the harness therefore renders the prompt itself and uses the raw generate endpoint.

6. Experiments and results

6.1 Design

Same questions, same tools and same model in every row; only the harness flags change. Profiles: A raw LLM (no tools); B LLM + tools; C tools + stateful harness (the model calls everything); D + evidence/quality gate, policy label shown to the model, enforcement (retry and safe fallback); E + memory and human review. Models: base gemma3:4b and fine-tuned gemma3-bist-v23; temperature 0, seed 42, 8,192 context. Questions: 40 held-out test questions (proportionally sampled by type, 5 of them macro); 40 × 2 models × 5 profiles = 400 sessions, run on a Kaggle T4 in 13,160 s. For reproducibility, the fine-tuned model was run on 19 questions twice in profile D (38 sessions). The maximum number of model turns per session is 40 (TURN_LIMIT).

6.3 What fine-tuning improved, and what it did not

  • Base → fine-tuned, full harness (D): delivered answers 1/40 → 30/40; the base model almost never produced a valid tool call in D/E (36 sessions ended in a model error). In the tools-only profile (B) numerical hallucination fell from 83.3% to 0.0%; in profile C delivery rose from 12/40 to 31/40.
  • Earlier fine-tuned model (75 steps) → final (120 steps), D/E: delivered 23/40 → 30/40; cut-offs (TURN_LIMIT) 17 → 10; unevidenced numbers 18.2% → 11.8%; label = expected label 78.3% → 80.0%; hallucination and delivered rule violations stayed 0. First-call accuracy of the final model (tool name correct / parameters identical to the teacher call, 18 test questions): 14/18 and 8/18 (first model generation, v2.1: 6/18 identical).
  • What got worse (reported honestly): in the unprotected profiles the 120-step model is worse than the earlier one: in C, delivery 40 → 31 and hallucination 0% → 22.2%; in B, rule violations 7.7% → 36.8%. Reproducibility fell from 57.9% to 47.4%. The safety of delivered answers comes from the harness, not from the model.
  • Architecture effect (A → D, same model): hallucination 100% (no tools) → 0% once tools are added (B) → delivered rule violations 22.6% with the state machine alone (C) → 0% with evidence lock, number verifier and action guard (D). Profile E (memory and review) gave the same results as D in this protocol, i.e. no measurable additional effect.

6.4 Harness additions made after the evaluation

Why sessions were cut off. In the 10 remaining cut-off sessions the model repeated the same invalid call in about 38 of 40 turns. We reproduced one case locally: for “how are TTKOM's current and liquidity ratios in the last quarter?” the model called get_fundamental_metrics with period="Q3" (valid format: 2026Q3) and repeated the same invalid call (the Kaggle run ended with 39 of 40 turns invalid); the error text shows the pattern but the 4B model cannot infer the format.

Parameter fixer (harness/param_fixer.py). Only when schema validation fails, the harness repairs formatting mistakes deterministically before the tool runs: period spelling (2026-Q3, Q3 2026, 2026/Q3 to 2026Q3; a year-less “Q3” that means the latest ended quarter drops the period field so the tool uses the latest disclosed period), enum letter case (Ichimoku to ICHIMOKU, only when the match is unique), and removal of fields that do not exist in the tool contract. as_of is never modified; ambiguous values (“last quarter”, “latest”) are not guessed; every repair is recorded as a PARAMS_NORMALIZED log event, a session warning, and in the real params/input_hash of the envelope. It can be switched off with HARNESS_NORMALIZE_PARAMS=0. Unfixable period errors now carry a format hint. Running the instructor's five sample questions locally (below) exposed four further format-level loops, each fixed deterministically in the same way: (1) a mistyped ticker (ERGL for EREGL) is corrected only when exactly one universe ticker named in the question is within edit distance 2; (2) a split_date equal to the analysis start (which the tool rejects) is moved to 1 January of the as_of year, the rule stated in the system prompt; (3) strategy.signal_params keys that the backtest tool does not define (e.g. rsi_state) are dropped; (4) the tool-call parser accepts a valid JSON object followed only by surplus closing brackets (the model often wrote }}}}}), while any other trailing text is still an error. Each repair is logged and listed in the warnings as above.

Local verification (single example, not a statistical result). The TTKOM question that ran 40 turns without an answer in the Kaggle evaluation was re-run locally with the fixer: delivered in 3 model turns (130 s on CPU), label INVESTIGATE (equal to the policy label), 5 number claims, 0 hallucinated, 0 unevidenced, 0 rule violations. The model's call period="Q3" was normalized by the harness (the 2026Q3 statement was not yet disclosed on 2026-11-13; the tool correctly used 2026Q2). We did not run a controlled A/B experiment of the fixer on all 40 questions: on a CPU every turn re-processes the whole prompt (Section 9, L50) and the 10 cut-off sessions would take over 10 hours. The model-only numbers in Section 6.2 therefore do not include the fixer.

Scope guard (harness/scope_guard.py). A question with no universe ticker and no finance keyword (e.g. “What will the weather in Istanbul be tomorrow?”) previously made the model call an unrelated tool and spend about 18 minutes on a CPU. The demo commands now answer such questions instantly without running the model: a short out-of-scope message ending with EYLEM: ANALYSIS_UNSAFE (no advice, no price target). The guard is deliberately conservative (when in doubt the question goes to the model) and none of the 750 training, validation and test questions is classified as out of scope. The instructor's documents do not define the expected behavior for non-financial questions; we chose the allowed action ANALYSIS_UNSAFE (“analysis cannot be done safely”); INVESTIGATE would be an equally defensible reading of “if evidence is insufficient, say INVESTIGATE or ANALYSIS_UNSAFE”.

6.5 Speed and hardware

On a Kaggle T4 the average session takes 30.8 s in profile D (400 sessions in 3.66 hours). On a CPU-only machine we measured about 26 prompt tokens per second; Ollama's log shows forcing full prompt re-processing due to lack of cache data (likely due to SWA ...), i.e. Gemma 3's sliding-window attention prevents prefix-cache reuse, so the whole ~4,000-token prompt is processed again on every turn (≈160 s per turn). A delivered 4–6 turn session therefore takes roughly 10–20 minutes on a CPU and a 40-turn cut-off session about 100 minutes. A machine with a dedicated NVIDIA GPU (≥ 4 GB VRAM) is recommended for live use; a pre-recorded session can be re-run with replay in seconds because the tools are deterministic and need no model.

9. Known limitations (summary; the full list L1–L50 is in docs/report/limitations.md)

  1. Training data. No POTENTIAL_CATCH_UP_CANDIDATE or FUNDAMENTAL_IMPROVEMENT_CANDIDATE examples exist (the policy produced none on real data); the label distribution is INVESTIGATE-heavy (63.5%); explanations are template-built from locked evidence, not written freely.
  2. Fundamentals. Source is Yahoo Finance and was not verified against KAP (except TUPRS disclosure dates); 21 disclosure dates are approximate; YoY is missing for many quarters; the fundamentals policy and thresholds are provisional.
  3. Coverage. No news or speech tools; no policy-rate series (CBRT funding cost is used); relate_to works on daily series and short samples only; 11 of 30 stocks have no sector peers.
  4. Model quality. About 25% of full-harness sessions end at the turn limit (safe fallback, but no answer); first-call accuracy is 14/18 for the tool name and 8/18 for identical parameters; without the harness the model is unreliable (profiles B and C); the 120-step model is worse than the 75-step model in profiles B and C. We compared only one base model.
  5. Reproducibility. Live reproducibility is 47.4% despite temperature 0 and a fixed seed (GPU/Ollama numerical non-determinism). Tools and harness are deterministic and a recorded session replays bit-for-bit; live regeneration of the same text is not guaranteed. Labels and numbers do not change because they come from tools and policy.
  6. Context and speed. The longest evaluated prompt was 8,191 tokens against an 8,192 limit; on CPU every turn re-processes the full prompt (Gemma 3 SWA), making hard questions take up to about 100 minutes.
  7. Statistics. Small samples, multiple testing (corrected where tests are declared), no causal claims; backtests include costs and benchmarks but are subject to selection bias. Correlation is not causation; past is not future; LLM confidence is not a probability.
  8. Metric caveat. The number verifier is a lower bound (small integers can match by chance; numbers written as words and direction are not checked); the invalid-call rate is inflated by rejected text turns.
  9. Evaluation scope. One run of 40 questions per condition (no confidence intervals); the fixer and scope guard were added after the measurements and are verified by tests and one real example rather than a controlled experiment.

10. Conclusion, reproducibility and deliverables

Conclusion. The project follows the course principle: the LLM interprets and explains, Python tools compute, the harness controls, the backtest verifies, and the model runs locally. Fine-tuning made the small model usable inside the harness (1/40 to 30/40 delivered answers in the full harness; 83.3% to 0% hallucination with tools), and the harness, not the model, guarantees that delivered answers contain no invented numbers, no rule violations and a policy-consistent action label. The main open problems are the 25% of sessions that end at the turn limit, live reproducibility, and the model's weakness without the harness. Future work: a news/KAP and speech layer; KAP-verified fundamentals and more history (YoY and the FUNDAMENTAL_IMPROVEMENT_CANDIDATE examples); controlled A/B evaluation of the parameter fixer and a larger question set with confidence intervals; training data with first-call corrections for the weak question types; a GPU-based reproducibility study.
